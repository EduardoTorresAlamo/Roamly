1. Three-file indirection chain for the trip context High

Shallow modules · tight coupling · src/hooks/useTrips.ts

The trip context is spread across three files where one deep module would do. Data + provider live in TripContext.tsx; the raw contexts and their accessor hooks live in useTripContext.ts; then useTrips.ts re-exports those same hooks under renamed aliases and adds zero behavior. Every consumer imports the third file, so a reader chasing useTripActions hops through two pure pass-throughs before reaching logic.

useTrips.ts is 17 lines, 12 of them comment/JSDoc, and its whole body is export { useTripState as useTrips, useTripDispatch as useTripActions, useTripById }. The split of state-vs-dispatch context (in useTripContext.ts) is a legitimate re-render optimization — the extra rename layer on top of it is not.
Fix: collapse useTrips.ts into useTripContext.ts — export the public names (useTrips, useTripActions, useTripById) directly from where the hooks are defined. Two files, one import path, no rename hop. Keeps the state/dispatch context split intact.

2. Comment-to-code inversion (AI slop) Medium

Redundant / over-explaining comments · utils + hooks + context

Several modules carry more comment than code, restating what the code already says. generateId is a one-line Date.now() + Math.random() wrapped in a 9-line essay on collision probability. The signal (the genuinely useful notes — StrictMode idempotency, out-of-order Overpass responses) is buried in equal volume of narration of the obvious.

Not all comments are slop — keep the why (why split contexts, why debounce 300ms, why idempotent upsert). Cut the what: JSDoc that repeats the type signature, and inline comments narrating each .map() traversal in TripContext.tsx.
Fix: delete comments that restate the signature or the next line. Target ratio for leaf utils: under ~25%. Keep the non-obvious rationale blocks.

3. Testable pure logic trapped inside a page component Medium

Hard-to-test code path · src/pages/TripDetail.tsx

generateItineraryMarkdown(trip) is a pure, deterministic serializer — exactly the kind of function that should have unit tests. But it is a private, un-exported function inside a 406-line page component, so it cannot be reached from a test without rendering the whole page. Its sibling generateTripICS (same shape, trip → string) lives in utils/icsExport.ts, is exported, and has tests (icsExport.test.ts). Same job, opposite testability — purely because of file placement.

Same finding blocks the two export handlers: handleExport / handleExportCalendar mix pure serialization with navigator.clipboard, blob URLs, and trip! non-null assertions — untestable side effects wrapped around testable logic.
Fix: move generateItineraryMarkdown into utils/itineraryMarkdown.ts and export it, mirroring icsExport.ts. Add a unit test alongside. The page then just calls it — the pure/impure boundary lands on a file boundary.
